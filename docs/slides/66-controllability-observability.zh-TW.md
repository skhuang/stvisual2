## 是什麼讓程式碼可測試？

在我們能夠生成一個測試、執行它、並信任它的判定之前，程式碼必須*讓*我們做得到。**可測試性**就是衡量它做到有多容易的性質。

經典的定義——來自 Freedman、來自 Binder，源頭在控制理論——把可測試性拆成兩個獨立的一半：

- **可控制性（controllability）**——測試能不能把軟體**驅動**到它需要演練的狀態或輸入？
- **可觀測性（observability）**——測試能不能**看見**它需要檢查的效果？

一個測試*兩者都需要*。如果你無法把程式碼導向你想測試的情境，你就永遠到不了那個行為。如果你到得了卻無法觀測結果，你就分不出通過與失敗。本講在一個小模型上把每一半都具體化。

<!-- 先建立框架：可測試性不是模糊的「乾淨程式碼」美德——它是兩個可衡量、可分離的能力。可控制性關乎*輸入*端（進得去），可觀測性關乎*輸出*端（讀得回來）。整份講義是一個兩欄的論證：一欄一半，各自錨定在同一個旋轉閘門上，讓學生看見它們是正交的。點名脈絡——Freedman、Binder、控制理論——讓學生知道這是一個定義，而非我們的發明。 -->

## 旋轉閘門 — 一個模型，兩個課題

我們使用一個刻意極小的受測系統（SUT）：一個**投幣旋轉閘門**，建模為一個確定性有限狀態機。

| 部分 | 值 |
| --- | --- |
| 輸入（測試的操縱桿） | `coin`、`push`、`reset` |
| 狀態 | `LOCKED`、`UNLOCKED`、`PASSED`、`JAMMED`、`MAINT` |
| 起始狀態 | `LOCKED` |
| 每個狀態的可觀測輸出 | `LOCKED→red`、`UNLOCKED→green`、`PASSED→beep`、`JAMMED→green`、`MAINT→red` |

轉移恰好是：`coin` 解鎖，`push` 在解鎖時讓你通過，`reset` 重新上鎖——外加幾個自迴圈。關鍵是，**沒有任何輸入邊通往 `JAMMED` 或 `MAINT`**：卡住是一個故障，而維護需要一把測試手上沒有的實體鑰匙。

<!-- 介紹後面每張投影片都會讀取的固定裝置——它就是 src/data/testabilityModels.js 裡的 TURNSTILE_SUT，是探索器與其單元測試共用的唯一真相來源。強調兩個刻意手挑的缺口：JAMMED 與 MAINT 沒有進入的輸入驅動邊（可控制性陷阱），而 JAMMED 與 UNLOCKED 共用輸出 'green'（可觀測性陷阱）。後續一切都是這兩個模型設計選擇的後果。 -->

## 可控制性 — 定義

**可控制性**問：從初始狀態出發，只用測試能提供的輸入，測試**實際上到得了**哪些狀態？

用廣度優先搜尋（BFS）從起始狀態沿著轉移關係計算它，只跟隨輸入驅動的邊：

```
reachable(SUT) = 從 start 沿 trans 做 BFS      # 只用輸入
可控制性 = |reachable| / |states|
```

搜尋永遠到不了的任何狀態就是一個**可控制性缺口**：沒有任何測試輸入序列能把 SUT 放到那裡，因此沒有任何測試能演練住在那個狀態裡的行為。缺口不是一個漏掉的測試——它是一個測試在*結構上無法造訪*的狀態。

<!-- 這就是匯出的 reachableStates(sut) / controllability(sut) 引擎。訊息要俐落：可控制性是一個由 BFS 回答的可達性問題，其值是一個比率。教學重點是「缺口」的概念——一個不可達的狀態比一個未測試的狀態更糟，因為在設計改變之前，再多的寫測試功夫都無法覆蓋它。為下一張要揭曉的數字鋪路。 -->

## 旋轉閘門上的可控制性 — 3/5

從 `LOCKED` 執行可達性搜尋：

- `LOCKED` — 起點
- `LOCKED --coin--> UNLOCKED`
- `UNLOCKED --push--> PASSED`

可達集合 = **{ LOCKED, UNLOCKED, PASSED }** → **可控制性 3/5 = 60%**。

`JAMMED` 與 `MAINT` 就是**缺口**。沒有任何輸入（`coin`/`push`/`reset`）能把 SUT 驅動進這兩者：`JAMMED` 只由故障進入，`MAINT` 只由一把不屬於測試輸入的維護鑰匙進入。一個測試套件就是*無法*把旋轉閘門放到那些狀態——「卡住處理」與「維護」行為從外部是不可達的。

<!-- 把 BFS 大聲走一遍，讓 3/5 是掙來的、而非斷言的。兩個不可達狀態正是這個模型的重點。問全班：你會怎麼讓 JAMMED 變得可控制？（加一條只給測試用的輸入邊——一個故障注入掛鉤——這正是一個為可測試性而做的接縫，預告第 2 個探索器。）比率 3/5 = 60% 必須與探索器的讀數完全一致。 -->

## 可觀測性 — 定義

**可觀測性**問一個鏡像的問題：如果一個故障落在某個狀態，測試**分辨得出來嗎**——那個狀態是否產生一個可區分的輸出？

當一個狀態的輸出值在所有狀態中是**唯一**的，它就是可觀測的。如果兩個狀態共用一個輸出，只看輸出的觀測者就無法區分它們，因此一個把其中一個換成另一個的故障就是不可見的。

```
observable(SUT) = 輸出在所有狀態中為唯一的那些狀態
可觀測性 = |observable| / |states|
```

共用的輸出、被吞掉的錯誤、缺失的回傳值，都會把不同的內部情境塌縮成一個外部訊號——而每一次塌縮都藏起一個潛在故障。

<!-- 這是 observableStates(sut) / observability(sut)。這裡用的定義刻意簡單而精確：一個被兩個狀態共用的輸出使兩者都不可觀測，因為外界無法區分它們。連結到真實程式碼：兩條都回傳 null、或都記錄相同訊息的錯誤路徑，正是兩個狀態共用 'green' 的同一種失效模式。可觀測性是硬幣的輸出面，與可控制性正交。 -->

---

## 旋轉閘門上的可觀測性 — 1/5

清點輸出：

| 輸出 | 具此輸出的狀態 | 唯一？ |
| --- | --- | --- |
| `red` | LOCKED、MAINT | 共用 |
| `green` | UNLOCKED、JAMMED | 共用 |
| `beep` | PASSED | 唯一 |

只有 **PASSED → `beep`** 是唯一的 → **可觀測性 1/5 = 20%**。

最要命的案例是 `green`：**`JAMMED` 看起來與 `UNLOCKED` 一模一樣**。從外部看，一個卡住的旋轉閘門與一個正常解鎖的閘門發出相同的訊號——因此測試永遠無法靠看輸出來抓到卡住。故障是真的，但它是不可見的。

<!-- 基礎可觀測性刻意低到不行（1/5），好讓設計選擇那張投影片重重落地。JAMMED/UNLOCKED 的碰撞就是那個具體課題：這是經典的「兩種失效模式、一個輸出」臭蟲，它熬過每一個測試，因為沒有任何斷言能把它們分開。1/5 = 20% 必須與探索器一致。留意與可控制性的不對稱：JAMMED 既不可控制*又*不可觀測，這正是為何真實的卡住會溜過去。 -->

## 可觀測性是一種設計選擇

可觀測性不是被問題固定住的——它是開發者**設計進去**的東西。加一個可區分的輸出，先前隱藏的狀態就變得可見。

在探索器裡，切換**「加一個探針」**：它給 `JAMMED` 一個自己的獨特輸出 `grind`，而非沿用 `green`。重新清點：

| 輸出 | 狀態 | 唯一？ |
| --- | --- | --- |
| `red` | LOCKED、MAINT | 共用 |
| `green` | UNLOCKED | **現在唯一** |
| `beep` | PASSED | 唯一 |
| `grind` | JAMMED | **現在唯一** |

可觀測性從 **1/5 跳到 3/5 = 60%**——一個探針修好了*兩個*狀態，因為把 `JAMMED` 分離出來，也讓 `UNLOCKED` 的 `green` 不再共用。

<!-- 樞紐的一張：可觀測性是一根槓桿，不是宿命。探針是任何加上去的回傳值、日誌行、狀態欄位、或只給測試用的存取器，讓一個內部狀態變得可區分。這個雙贏值得停下來講：為 JAMMED 加一個獨特輸出也救回了 UNLOCKED，因為 green 之所以模稜兩可，就只是因為那個碰撞——所以計數走 1/5 → 3/5，而非 1/5 → 2/5。這正是引擎裡 withProbe(sut, 'JAMMED', 'grind') 的路徑；數字必須一致。 -->

## 逐步演練 — 驅動到 PASSED

把兩半合起來，針對一個具體的測試目標：**驗證通過行為**（狀態 `PASSED`，輸出 `beep`）。

- **可控制性**：`PASSED` 可達嗎？可以。從 `LOCKED` 出發的最短驅動：

  ```
  coin   →  UNLOCKED
  push   →  PASSED
  ```

  兩個輸入——測試的設定序列自己就寫出來了。

- **可觀測性**：到了那裡之後,測試檢查得了嗎？可以——`PASSED` 發出 `beep`，那個唯一的輸出，因此斷言 `expect(output).toBe('beep')` 把它與其他每一個狀態區分開來。

`PASSED` 完全可測試，因為它既可達*又*可區分。對比 `JAMMED`：靠輸入不可達，**而且**（在加探針之前）與 `UNLOCKED` 不可區分——在兩個軸上都不可測試。

<!-- 用一個端到端的測試設計故事把整份講義綁起來。driveTo(sut,'PASSED') = [coin, push] 是匯出的 BFS；那個序列就是一個真實測試的 arrange 步驟。beep 是唯一的,正是讓 assert 步驟成為可能的原因。與 JAMMED 的對比顯示兩個軸是獨立的但缺一不可：一個狀態需要可控制性來 arrange、需要可觀測性來 assert。這是學生寫真實測試時該帶著的心智模型。 -->

## 為何兩者對測試設計都重要

每一個測試都有一個 **arrange（安排）** 步驟與一個 **assert（斷言）** 步驟，而它們恰好對映到兩半：

- **Arrange 需要可控制性。** 設定把 SUT 驅動到受測狀態。一個不可控制的狀態沒有能到達它的 arrange 步驟——測試根本無從開始。
- **Assert 需要可觀測性。** 檢查讀取一個輸出並比對。一個不可觀測的狀態沒有能區分通過與失敗的輸出——斷言毫無意義。

所以當一個單元「難以測試」時，問*是哪一半*出了問題。安排不了情境？可控制性——加一個接縫或一個只給測試用的輸入。驗證不了結果？可觀測性——加一個回傳值、一個探針、一個狀態欄位。點名那一半，就把一個模糊的抱怨變成一個具體的設計修復。

<!-- 可行動的重點：每一個測試的 arrange/assert 結構就是可控制性/可觀測性的分野在偽裝。這給學生一個診斷法：當他們撞上一個不可測試的單元,把困難分解成兩個軸，每個軸都指向一個具體的補救。預告本章節其餘部分——第 2 個探索器（接縫）是可控制性的補救工具箱，而探針／回傳值是可觀測性的補救。 -->

## 小結

- **可測試性 = 可控制性 + 可觀測性**——經典的兩部分定義。一個測試兩者都需要：一個用來抵達行為，一個用來檢查它。
- **可控制性** = 測試能否把 SUT 驅動到需要的狀態？以從起點沿輸入驅動邊的可達性（BFS）衡量。在旋轉閘門上：可達 **{ LOCKED, UNLOCKED, PASSED } = 3/5**；`JAMMED` 與 `MAINT` 是缺口——沒有輸入到得了。
- **可觀測性** = 測試能否看見效果？以有多少狀態具有**唯一**輸出來衡量。在旋轉閘門上只有 `PASSED → beep` 是唯一的，所以基礎可觀測性是 **1/5**；`JAMMED` 與 `UNLOCKED` 共用 `green`，因此卡住是不可見的。
- **可觀測性是一種設計選擇。** 加一個探針（`JAMMED → grind`）把可觀測性提升到 **3/5**，因為區分 `JAMMED` 也讓 `UNLOCKED` 的輸出不再共用。
- **兩者都對映到每一個測試**：arrange 需要可控制性，assert 需要可觀測性。當一個單元難以測試,點名出問題的那一半——補救就隨之而來。

**課堂練習：** 對於旋轉閘門，給出把它驅動到 `PASSED` 的最短輸入序列（答案：`coin · push`），再解釋為何一個落在 `JAMMED` 的故障在加探針之前會逃過每一個測試，以及一個 `grind` 探針究竟讓哪兩個狀態變得可觀測。
